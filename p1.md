FEATURE A: RESUME PERSONALISATION
1. Reuse the extracted resume text and user information already stored by Phase 1; do not require users to upload the same resume again.
2. Provide an explicit Analyse/Update Resume action accessible from Add/Update Resume.
3. Analyse resume text using the user's own decrypted Groq key only when needed.
4. Extract a structured profile containing target roles, skills, programming languages, frameworks, database technologies, projects, experience and recommended interview topics. Distinguish facts stated in the resume from uncertain inferences.
5. Ask the LLM for structured JSON, validate it against an application schema, and handle malformed or incomplete output safely. Do not trust model-generated JSON without validation.
6. Treat resume content as untrusted data. Instructions embedded in a resume must never override system instructions or trigger arbitrary tools or actions.
7. Store validated derived information in SQLite. Reuse the analysis when the resume content has not changed. Invalidate stale analysis after resume replacement or deletion.
8. Show a concise summary of extracted skills and suggested topics, with buttons to accept or change the target role and recommendations.
9. If the API key is invalid, revoked, rate-limited or unavailable, preserve the resume and existing profile, explain the failure, and offer retry. Never fall back to another user's credentials.
10. Keep raw resume data private and provide a way to replace or delete it using the existing account/data-management implementation.

FEATURE B: QUESTION BANK
1. Add a version-controlled JSON question bank at a suitable location such as data/question_bank.json, unless Phase 1 already has an appropriate implementation.
2. Include the following categories:
   - DSA
   - DBMS / SQL
   - OOP / Java
   - Operating Systems
   - Computer Networks
   - AI / ML
   - Resume / Projects
   - HR / Aptitude
   - Web / Backend Development
3. Seed at least 10 useful, non-duplicated questions per category, with a total of at least 90 curated questions.
4. Each question should have a stable ID, topic slug, subtopic, difficulty, question text, useful tags, concise hint, expected key concepts and a clear model answer. Add follow-up questions where appropriate.
5. Include meaningful easy, medium and hard coverage. Check technical accuracy; do not generate repetitive filler just to reach the required count.
6. Validate every question record at startup or in a dedicated validation command. Fail with a clear error for duplicate IDs, invalid topics, missing answers or invalid difficulty.
7. Initialise or import questions idempotently. Restarting the app must not create duplicate questions or overwrite user history.
8. Keep question content independent of API keys, user data and runtime-generated LLM output.

FEATURE C: CHOOSE TOPICS
1. Implement the existing Choose Topics menu item using Telegram inline keyboards.
2. Let users select multiple topics and deselect them. Use readable labels and stable topic slugs.
3. Show the current selection clearly. Provide Save, Cancel and Back actions.
4. Persist the selection against the Telegram user ID in SQLite.
5. Validate selections against the known topic list.
6. Make the interface mobile-friendly and avoid Telegram callback_data limits.
7. Changing topics must not erase past performance or unrelated settings.
8. Provide a helpful first-use state when the user has not chosen topics.

FEATURE D: RANDOM TOPIC PRACTICE
1. Activate the Random Topic Practice menu item.
2. Select a random topic from the user's selected topics, followed by a random question from that topic.
3. Avoid immediately repeating recently presented questions where possible. If every eligible question has been used, cycle fairly instead of becoming stuck.
4. Persist question history so restarting the process does not erase repeat-avoidance history.
5. Display the topic, difficulty, question and concise navigation controls:
   - Next Question
   - Show Hint
   - Reveal Model Answer
   - Change Topics
   - Back to Menu
6. Do not reveal the model answer until explicitly requested.
7. If no topic is selected, guide the user to Choose Topics rather than crashing or silently choosing a misleading category.
8. If a category has no eligible questions, show a friendly message and record a useful diagnostic without exposing private data.
9. Use callback handlers that verify ownership of the interaction. One user must never be able to operate another user's session by replaying callback data.
10. Ensure that navigation remains usable after timeouts, repeated button presses and bot restarts.

FEATURE E: TEACH ME A TOPIC
1. Activate the existing Teach Me a Topic menu item.
2. Ask the user to enter a topic, such as SQL indexing, Java inheritance, operating-system scheduling or REST APIs.
3. Use only that user's existing Groq BYOK configuration. The onboarding policy requires a valid key; handle revoked or invalid credentials with a clear recovery message.
4. Produce an understandable English lesson with:
   - A simple definition.
   - A step-by-step explanation.
   - A practical example or analogy.
   - An interview-ready explanation.
   - Three relevant practice questions.
5. Keep answers appropriately concise for Telegram, split long messages safely and avoid unbounded outputs.
6. Use a configurable model from existing settings; do not scatter model names or API parameters throughout handlers.
7. Handle network timeouts, rate limits, invalid credentials, provider errors, malformed responses and Telegram message-length limits.
8. Bound retries and use timeouts. Do not retry permanent errors endlessly.
9. Treat user-provided text as a topic request, not as permission to execute instructions, tools or arbitrary code.
10. Provide Try Another Topic, Continue Learning and Back to Menu actions where appropriate.
11. Do not build a second AI client, duplicate credential-storage logic, or log prompts containing private resume information.
